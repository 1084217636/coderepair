# 21 AI 辅助 Agent 开发：真实故障、工作差异与面试口径

这一章不再增加概念名词，而是把本项目实际遇到的问题变成可复用的开发方法。面试中，比“我知道 RAG、Tool、Agent”更有说服力的是：你能说明一次失败怎样被发现、如何缩小范围、修复依据是什么，以及哪些风险仍未解决。

## AI 辅助开发的正确顺序

1. 先写目标、不变量和禁止事项，例如 Patch 只能改允许路径、测试命令必须来自服务端模板、模型不能直接批准自己的结果。
2. 让 AI 帮助定位相关文件、已有测试和调用链，不直接要求它一次生成大改动。
3. 把概率性部分和确定性部分分开：模型负责提出候选，代码负责路径校验、状态流转、执行门禁和审计。
4. 先补失败用例，再做小批量修改；每次都检查 staged diff，避免生成物、密钥和无关改动混入提交。
5. 本地依次运行后端检查、前端检查、测试和固定评测集；推送后再看远端 CI 的第一个真实错误。
6. 记录“现象—假设—证据—修复—残余风险”，让故障成为项目证据，而不是只留下一个绿色勾。

AI 可以加快代码定位、测试草拟和文档整理，但不能替代对状态机、安全边界、测试有效性和最终 diff 的判断。你必须能解释每一处关键修改，否则它不能算作自己的项目能力。

## 本项目真实遇到的故障

### 1. 本地缺少 Node 与 pnpm，前端门禁被跳过

后端检查和测试通过，并不代表整个仓库通过。当时本机没有 Node/pnpm，因此无法运行前端 `pnpm check` 和 `pnpm test`；第一次远端 CI 随后发现 import/order 错误。

处理方法是安装用户级 Node 22 与 pnpm 10，重新执行前端检查和全部 463 个测试。这个案例说明：缺少工具时应明确写成“某门禁未执行”，不能把部分通过概括成项目通过。

### 2. 远端 CI 的第一个失败来自格式规则

远端运行 `32629830024` 中，后端任务通过，前端任务因 `AnchoredBranchPanel` 的导入顺序失败。修复 import/order 时，又一并处理了 Code Change Console 的 Hook dependency 警告；提交 `eb0a3edd` 后，运行 `32629900141` 的后端与前端任务均通过。

排查顺序应是：先确认失败 Job，再找第一个失败 Step，最后定位第一条有文件和行号的错误。不要被后续级联日志干扰，也不要因为本地测试通过就否认 CI 的环境差异。

消除前端 warning 后的下一次运行又在测试开始前失败：`corepack prepare pnpm` 的下载解析触发 Node `undici` 断言。由于失败发生在依赖引导步骤，不能归因于刚修改的 React 代码。最终改用 `pnpm/action-setup` 固定 pnpm 版本，并让 `setup-node` 管理 pnpm 缓存。这个过程体现了“先看失败阶段，再判断代码是否相关”，也比盲目重跑更容易留下稳定门禁。

### 3. 工作流没有覆盖功能分支

工作流曾只监听主分支。功能分支推送后没有运行记录，这不是“CI 成功”，而是根本没有执行。修复时需要同时检查 `on.push.branches`、`pull_request`、路径过滤和仓库 Actions 页面。

### 4. 评测产物差点混入提交

固定评测会生成 JSON 报告，它们属于运行证据，不一定属于源码。处理方式是删除误生成文件、补充 `.gitignore`，并让 CI 使用 artifact 保存结果。提交前查看 staged diff 是最后一道低成本防线。

### 5. 固定 20 题不等于真实线上效果

当前 20 个外部 Patch 与 fake-model 用例能够证明路径防护、Patch 应用、测试门禁和状态转换可重复运行，但不能证明在线模型修复率，也不能推出人工接受率。面试时要把“机制正确性”和“模型效果”分开说明。

## Agent 项目更容易遇到什么问题

- 模型与 Provider：限流、超时、响应结构变化、token 超限、输出漂移、重试导致重复副作用。
- Context 与检索：召回文件不相关、遗漏跨文件依赖、上下文过长、旧摘要污染、提示注入进入检索结果。
- Tool：参数 schema 与真实权限不一致、超时和半成功、重复调用、并发竞争、模型把工具可用误解为已经授权。
- Patch 与执行：diff 格式正确但语义错误、测试覆盖不足、命令注入、路径逃逸、工作区污染和资源耗尽。
- 系统与协作：状态不可追踪、缺少 trace、成本无法归因、人工审批形同虚设、上游框架升级造成二开冲突。

遇到这些问题时，优先增加可观测证据和确定性边界，而不是继续堆提示词。

## 当前项目与真实工作的差异

| 维度 | 当前项目能证明 | 公司环境通常还需要 |
| --- | --- | --- |
| 上游维护 | 基于 DeerFlow 二次开发并区分上游/个人代码 | 长期 fork 策略、升级回归、依赖漏洞和跨团队 ownership |
| 检索 | 轻量仓库扫描和受预算约束的上下文 | 增量索引、权限过滤、缓存、召回评测与大仓性能 |
| 模型评测 | fake model 与固定 20 题可重复测试 | 多模型、多版本、真实任务集、人工标注、回归阈值与成本比较 |
| 执行隔离 | 本地副本、受限命令和路径校验 | 容器/微虚机、网络与资源配额、镜像治理、恶意仓库防护 |
| 控制面 | 文件化任务状态、人工审批与 PR handoff | 数据库、队列、多租户、幂等、并发恢复、GitHub App 权限与审计 |
| 可观测性 | 结构化报告和基本错误记录 | trace、token/费用、SLO、告警、值班和事故复盘 |
| 交付流程 | 个人完成需求、测试和 CI | 产品验收、安全评审、灰度、回滚、数据与法务协作 |

所以简历应写“实现了什么、用什么测试证明、边界在哪里”，不要把学习型项目包装成已经承载真实生产流量的平台。

## 秋招面试怎么说

### 一分钟版本

> 我基于 DeerFlow 做了一个可审计的 Coding Agent。模型只能通过最小权限 Tool 搜索和读取代码，再提交 typed patch；服务端负责路径校验、固定测试模板、状态机、报告和人工审批。我还实现了 Anchored Branch Context，让局部讨论在预算内继承上下文，并通过结构化 Decision 回流主线程。项目用后端测试、前端测试、固定 20 题评测和远端 CI 验证机制，同时明确没有把本地 Workspace 描述成生产级 Sandbox，也不声称固定用例等于线上模型修复率。

### 被问“AI 写了多少”

可以回答：AI 用于代码定位、候选实现、测试草稿和文档整理；你负责需求边界、架构取舍、逐行 diff 审查、失败复现、门禁设计和最终验证。随后举 import/order CI 故障或评测产物治理的例子，证明你不是只接受生成结果。

### 被问“最难的问题”

不要回答“Prompt 很难调”。更好的答案是：如何把不稳定的模型输出限制在可审计的确定性流程中。结合 Tool schema、路径白名单、fencing/状态转换、服务端测试模板、HITL 和评测解释设计取舍。

### 被问“如果进入公司下一步做什么”

按优先级回答：真实容器隔离和资源配额；数据库/队列与幂等恢复；真实 GitHub App 权限和审计；多模型离线评测加线上 trace；最后才是扩大自动执行范围。

## 把知识点变成开发练习

1. 故意制造一个 Tool 参数错误，记录模型输出、校验错误和最终状态。
2. 给检索加入一个跨文件问题，比较 top-k 改变前后的召回和 token 成本。
3. 构造越界路径、重复 Patch、超时测试和中断恢复四个负向用例。
4. 把一个 fake-model 用例换成真实 Provider，但单独记录模型名、版本、温度、成本和不可重复性。
5. 为一次失败写五段式复盘：现象、影响、根因、修复、预防；面试前至少积累三篇。

## 本章代码阅读任务

- 阅读顺序：先读 `.github/workflows/code-change-platform.yml` 的实际门禁，再读 `backend/src/deerflow/code_change/agent_patch.py` 和 `backend/src/deerflow/anchored_branch/`，最后对照 `backend/tests/code_change/`、评测脚本与前端 Code Change Console。
- 看到什么程度：能指出概率性决策在哪里结束、确定性校验在哪里开始，并为每条简历表述找到实现、测试或 CI 证据。
- 暂不要求：不要求把固定评测结果外推为线上收益，也不要求背诵未实际接入的生产组件。
- 验收动作：完成三篇真实故障复盘，闭卷讲清一次 CI 修复和一次 Agent 安全取舍，并能说明仍然存在的风险。

## 参考答案

1. 因为分支或路径过滤可能使工作流根本未执行；只有确认对应 commit 的 Job 和 Step 都成功，才有通过证据。
2. 需求与权限边界、架构取舍、关键 diff 审查、测试是否有效、失败根因、数据和密钥安全，以及是否允许产生外部副作用。
3. 用例规模小、模型可能是 fake、任务分布固定，也没有真实用户与人工标注；它主要验证机制和回归，不代表线上分布。
4. 分别说明已经实现的机制、可复现证据、尚未完成的生产能力和下一步优先级，不使用“生产级”“高成功率”等无证据表述。
